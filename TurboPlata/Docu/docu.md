# TurboPlata — документация для дебилов

## 1. Что такое TurboPlata
TurboPlata — это система для швейного цеха, которая автоматически считает зарплату швеям за каждую операцию. Вместо бумажных талонов и ручного подсчёта всё работает через сканирование штрихкодов и само считает, сколько кому заплатить.

## 2. Кто чем занимается (роли)

- **Админ** — сидит за компом, создаёт заказы и техкарты.
- **Выдача** — сидит за компом, создаёт коробки и печатает маршрутники.
- **Швея** — стоит за столом с ESP32-сканером, шьёт, сканирует штрихкоды.
- **ОТК** — сидит за компом со сканером, проверяет готовые коробки.
- **Мастер** — сидит за компом, разруливает брак и ставит штрафы.

## 3. Как всё работает (по шагам, с примером)

**Пример:** заказ «Платье летнее», 100 штук, 3 операции.

### Шаг 1: Админ создаёт заказ
1. Заходит на страницу `/admin`
2. Вводит: название «Платье летнее», количество 100
3. Жмёт «Создать заказ»
4. Для заказа добавляет техкарту:
   - Шаг 1: «Стачивание боковых швов» — норма 120 секунд, разряд 2
   - Шаг 2: «Обмётка» — норма 90 секунд, разряд 1
   - Шаг 3: «Утюжка» — норма 60 секунд, разряд 1

### Шаг 2: Выдача создаёт коробку
1. Оператор выдачи заходит на главную страницу `/`
2. Авторизуется: вводит свой табельный номер
3. Выбирает изделие «Платье летнее»
4. Вводит количество: 25 штук
5. Жмёт «Создать коробку и напечатать маршрутник»
6. Сервер создаёт коробку #15 и печатает бумажку со штрихкодами:
   ```
   15-СТАЧИВАНИЕ БОКОВЫХ ШВОВ
   15-ОБМЁТКА
   15-УТЮЖКА
   ```
7. Бумажка клеится на коробку, коробка едет в цех

### Шаг 3: Швея шьёт
1. Швея Иванова подходит к столу #3
2. Сканирует свой табельный номер: `USER_100`
3. ESP32 пиликает — авторизация прошла
4. Берёт коробку #15, сканирует штрихкод `15-СТАЧИВАНИЕ БОКОВЫХ ШВОВ`
5. ESP32 пиликает — операция началась, таймер пошёл
6. Швея шьёт
7. Закончила — сканирует `DONE`
8. ESP32 пиликает — операция закрыта, сервер посчитал оплату

### Шаг 4: Следующая швея
1. Швея Петрова на столе #2 авторизуется: `USER_101`
2. Берёт ту же коробку #15, сканирует `15-ОБМЁТКА`
3. Шьёт → `DONE`

### Шаг 5: Всё готово — коробка едет на ОТК
Когда все 3 операции завершены, коробка автоматически переходит в статус «ожидает ОТК».

### Шаг 6: ОТК проверяет
1. Сотрудник ОТК за столом `otk-1` сканирует любой штрихкод с маршрутника
2. На экране появляется полный маршрутник с фамилиями:
   ```
   Коробка #15 — Платье летнее, 25 шт
   Шаг 1: Стачивание боковых швов — Иванова М.И. ✅
   Шаг 2: Обмётка — Петрова Е.А. ✅
   Шаг 3: Утюжка — Сидорова А.С. ✅
   ```
3. Сотрудник смотрит на коробку:
   - Всё хорошо → жмёт **«✅ Заебись»** → деньги готовы к выплате
   - Криво → жмёт **«❌ Брак»** → коробка в брак

### Шаг 7: Мастер разруливает брак
1. Мастер видит в `/master` коробку #15 в статусе «брак»
2. Идёт в цех, разбирается
3. Швея Иванова исправляет косяк (бесплатно, ничего не сканирует)
4. Мастер в `/master` жмёт «Принять после исправления»
5. Деньги становятся готовы к выплате

### Шаг 8: Конец дня — выплаты
В 20:00 сервер автоматически:
1. Собирает все записи «готово к выплате»
2. Группирует по швеям
3. Формирует XML-файл в папке `exports/`
4. Помечает записи как «выплачено»

## 4. Как считается зарплата

```
оплата = 50 руб × коэффициент_разряда × (норма / фактическое_время)
```

- Если швея уложилась в норму → 100% ставки
- Если шила дольше → оплата пропорционально меньше
- Если шила подозрительно быстро (< 10 сек) → сервер ставит флажок, мастер проверит
- Разряд 1 = ×1.0, разряд 2 = ×1.2, разряд 3 = ×1.5

## 5. Что означают статусы коробки

- **в_работе** — коробка в цехе, швеи шьют
- **ожидает_отк** — все операции завершены, едет на проверку
- **принята** — ОТК одобрил, молодцы
- **брак** — ОТК забраковал, мастер разбирается

## 6. Что означают статусы выплат

- **начислено** — операция выполнена, деньги посчитаны, но ещё не готовы
- **готово_к_выплате** — ОТК проверил коробку, деньги ждут nightly XML
- **выплачено** — ушло в XML, всё

## 7. Железки и компы

- У каждой швеи — стол с ESP32-сканером (WiFi). Никакого компа.
- У выдачи — комп с Go-клиентом + ESP32-сканер. Связаны в настройках.
- У ОТК — комп с Go-клиентом + ESP32-сканер. Связаны в настройках.
- У админа и мастера — просто комп с браузером.
- ESP32 и компы общаются **только** с сервером, не друг с другом.

## 8. Архитектура Go-сервера (файлы в `GO/`)

Сервер разделён на логические модули, каждый в своём файле:

| Файл | Что делает |
|------|-----------|
| **`main.go`** | Глобальные переменные, `main()`, роутинг, graceful shutdown, порт из `PORT` |
| **`logger.go`** | `setupLogging()` — лог-файл + stdout + окно PowerShell tail |
| **`database.go`** | `initDatabase()` — открытие трёх SQLite, `initSchema()` — миграции из `schema.json` |
| **`config.go`** | `loadConfigs()` — загрузка всех JSON, `handleConfig()` — API просмотра/сохранения формул, `setupWorkplacesFromConfig()` — обновление рабочих мест из `terminals.json` |
| **`backend_html.go`** | Сессии (cookie), `handleLogin/Logout/Session`, `servePage()` с проверкой роли, статика из `./HTML/` |
| **`logic.go`** | Вся бизнес-логика: `handleScan` (веб + MQTT), `processScanWithContext` (диспетчер), `handleDoneScan` (транзакция + аудит), `handleEmployees`, `handleOTK*`, `handleMaster*`, `handleBoxes`, `handleWorkerStats`, `handleAudit` |
| **`api.go`** | Коммуникации: MQTT, WebSocket (`handleWebSocket` + `handleBrowserWS` с проверкой сессии), REST API (`handleOrders`, `handleTechCards`, `handleWorkplaces`, `handleAuth`) |
| **`routines.go`** | Фоновые задачи: `backupRoutine` (бэкап БД каждые 15 мин + чистка старых), `cleanupRoutine` (чистка записей в 3:00), `nightlyExportRoutine` (XML выплат в 20:00) |

### Старые файлы удалены

`handlers.go`, `handle_employees.go`, `handle_otk_master.go`, `templates.go`, `utils.go`, `websocket.go`, `mqtt.go` — их код распределён по файлам выше.

Критичные API-ручки (`/api/employees`, `/api/config` POST, `/api/orders` POST/DELETE, `/api/boxes` POST, `/api/otk/*`, `/api/master/*`) проверяют роль через `requireRole()`. Даже зная endpoint, без нужной роли в сессии не выполнить.

## 9. PC-агент (`GO/PC/`) — привязка сканера к браузеру

PC-агент — маленькая программа, которая запускается на каждом компе (ОТК, Выдача) и отдаёт hostname компа браузеру.

### Зачем

Браузер не знает hostname компа. А серверу нужно знать, какой комп с каким ESP32-сканером связан, чтобы отправлять сканы в нужный браузер.

### Как работает

```
ESP32-сканер (esp32-otk-1)
    │
    ├── MQTT: factory/table/esp32-otk-1/scan
    ▼
Сервер TurboPlata
    │
    ├── смотрит terminals.json: esp32-otk-1 → COMP-OTK-1
    ├── шлёт результат через WebSocket на COMP-OTK-1
    ▼
Браузер на компе ОТК
    │
    ├── fetch('http://127.0.0.1:9999') → получает hostname
    ├── WebSocket → сервер: "я COMP-OTK-1"
    └── получает сканы с esp32-otk-1
```

### Файлы

| Файл | Назначение |
|------|-----------|
| **`main.go`** | Точка входа: `install`, `remove`, `run` |
| **`server.go`** | HTTP-сервер на `127.0.0.1:9999`, отдаёт `{"hostname":"..."}` |
| **`service_windows.go`** | Установка/удаление службы Windows (через SCM) |
| **`service_unix.go`** | Установка/удаление systemd-юнита Linux |

### Использование

```bash
# Windows — установить как службу (от админа)
pc-agent.exe install
# Запустить
sc start TurboPlataPCAgent

# Linux — установить как демон (от root)
./pc-agent install
systemctl start turboplata-pc

# Вручную (без установки)
pc-agent run
```

### Привязка в terminals.json

```json
{
  "workplaces": [
    { "id": "esp32-otk-1", "pc_hostname": "COMP-OTK-1", "role": "otk", "active": true },
    { "id": "esp32-vydacha-1", "pc_hostname": "COMP-VYDACHA-1", "role": "vydacha", "active": true }
  ]
}
```

`pc_hostname` = hostname компа, который отдаёт PC-агент.

## 10. Безопасность денег и транзакций

### Атомарность (транзакции)

Весь цикл начисления оплаты — **в одной SQLite-транзакции**:

```
BEGIN
  UPDATE журнал_выработки SET время_окончания
  UPDATE журнал_выработки SET сумма_начислена, статус_выплаты='начислено'
  UPDATE операции_коробки SET статус='завершена'
  INSERT INTO аудит
  [если есть следующая операция — создать запись в журнале]
COMMIT
```

Если сервер упадёт между BEGIN и COMMIT — откат. Деньги не пропадают.

### Идемпотентность

Перед начислением проверяется `сумма_начислена` в записи. Если там уже есть сумма — возвращается ошибка. **Двойной скан не даст двойной оплаты.**

### Аудит

Каждое событие с деньгами пишется в таблицу `аудит`:
- **начисление** — после DONE: кто, сколько, за какую операцию
- **штраф** — после штрафа от мастера: сколько списано, кто наложил

Админ смотрит лог в `/admin` → «Журнал аудита», выбор даты.

### Статусы выплаты (полный цикл)

1. **DONE** → `статус_выплаты = 'начислено'` — деньги посчитаны, заморожены
2. **ОТК: «Заебись»** → `статус_выплаты = 'готово_к_выплате'` — разморожены
3. **Мастер: «Принять после исправления»** → `'готово_к_выплате'` — если был брак
4. **20:00 XML-экспорт** → `статус_выплаты = 'выплачено'` — деньги в XML, ушли в бухгалтерию

Деньги **никогда** не попадают в отчёт без одобрения ОТК или мастера.

### Очистка бэкапов

`backupRoutine` каждые 15 минут пишет бэкап, **автоматически удаляет старше 7 дней**.
